## 6. Complément 2026-09-26 17:3x UTC (C-G2-4) — RFC 9162 §2.1.3.2, algorithme de vérification d'une preuve d'inclusion, tel que lu le 26/09 15:55Z (L-2)

Le §1 ne citait que l'ordre des deux hachages ; voici les étapes lues (paraphrase fidèle, structure et conditions conservées ; [lu] `https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1.3.2`) :
1. Si `leaf_index ≥ tree_size` : échec.
2. `fn ← leaf_index` ; `sn ← tree_size − 1` ; `r ← hash` (le hachage de feuille fourni).
3. Pour chaque `p` de `inclusion_path`, dans l'ordre : si `sn = 0` : échec (chemin trop long) ; si `LSB(fn)` est à 1, ou si `fn = sn` : `r ← HASH(0x01 ‖ p ‖ r)` puis, si `LSB(fn)` est à 0, décaler `fn` et `sn` à droite ensemble jusqu'à ce que `LSB(fn)` soit à 1 ou `fn = 0` ; sinon : `r ← HASH(0x01 ‖ r ‖ p)` ; enfin décaler `fn` et `sn` à droite d'un rang.
4. Fin : succès ssi `sn = 0` et `r = root_hash` (un chemin trop court laisse `sn ≠ 0` : échec).
Conséquence : un `verifyProof` conforme refuse un chemin trop long (étape 3, `sn = 0`) et trop court (étape 4) ; le test de C-G2-5 (taille annoncée n + 1) exerce exactement ce contrôle. Q-5 du journal G1 : levée par ce §6 (plus de recodage « de mémoire » : les étapes sont ici) ; le procurement (a) du journal est clos.
