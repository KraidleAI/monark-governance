## 3. Réponse à Q-V-3 bis : où `build` doit être vert

Trois portées possibles, avec ce qu elles exigent :
1. **Hôte seul** (état actuel) : `build` lit `F:/tmp` ; il est vert tant que l hôte garde ses fichiers ; le fait rr2 (branche supprimée ⇒ rouge) et la dépendance `F:/tmp` (volume déclaré temporaire) font que le journal ne survit ni à une purge ni à une réinstallation : c est la dette que (A) veut lever. Ne suffit pas.
2. **Clone `--no-local` du même hôte** (portée du cp-2 : le validateur rejoue `build` sur `clones/trunk`) : exige que les faits soient lisibles depuis le CLONE, donc dans le dépôt (arbre, ou objets sous une ref clonée), ou par un chemin d hôte absolu (ce qui redonne 1). Un clone lit les refs `refs/heads/*` par défaut, pas `refs/notes/*` ni `refs/journal/*` (mesuré).
3. **CI** : exige en plus que les faits soient dans ce que `actions/checkout` ramène (la seule branche, profondeur 1) ou fetchés explicitement par une ligne de la porte ; et qu aucun chemin `F:/` ne soit lu.

**Recommandation** : la portée à exiger de M-5c est la **2 (clone du même hôte)**, avec la **3 préparée** (aucun chemin d hôte dans le chemin de lecture des faits ; une ligne de `fetch` documentée pour la CI ; une porte CI `journal:build` = item formé, déclencheur : première CI verte sur le journal, GOLDEN-CI). Motif : c est la portée que le cp-2 exerce déjà en réel (CA-9 : rejeu sur clone), c est celle que la purge M-8b doit laisser verte, et c est la seule vérifiable sans acte investisseur (un push est un acte investisseur ; la CI ne se teste pas à blanc).
