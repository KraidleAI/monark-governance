## Context

On 2026-09-20 the 00:44 UTC sentinel run stopped on `no_quorum` (publicnode HTTP 403 while too few of the 8
free endpoints answered): `stopped != null`, `lag: 1`, `processedDays: []` — **and it exited 0**. Because the
unit is a `Type=oneshot`, `Restart=on-failure` would not have fired even if set (nothing failed, per the exit
code), so 2026-09-19 stayed unpublished for ~4 h until a manual relaunch at 04:58 UTC. The window's data was
identical on relaunch (archive blocks); only the delay changed (ADR-M012 D5: "a missed day is LAG, never a
skipped step"). Three causes compound: (a) a oneshot that exits 0 on a stopped day is invisible to systemd and
to any probe reading only the exit status; (b) the free pool has no paid, reliable operator; (c) nothing off
the VPS notices a stalled publication.

## Decisions

- **D1 — exit code carries the stop (L-1).** `run.ts` exits **1** iff `report.stopped !== null` (a fetch /
  quorum / c1 / unfinalized failure prevented catch-up), **0** otherwise (up to date, or waiting for finality
  — `due` empty or fully processed). The end JSON gains `exit_code`. Lines processed BEFORE a stop are written
  first; the non-zero exit is set after (partial catch-up is preserved, never rolled back). `runDue` sets
  `stopped` only with `lag >= 1`, so the plan's `lag > 0` is implied by `stopped !== null`.

- **D2 — the retry is four timer slots, not systemd `Restart=` (L-2).** `monark-sentinel.timer` fires at
  `00:30`, `03:30`, `06:30`, `09:30` UTC (four separate `OnCalendar=` lines — the single-line comma list
  `00:30,03:30,…` is an INVALID spec, C-2), `RandomizedDelaySec=1800`, `Persistent=true` (one boot catch-up,
  never one per missed slot). By 00:30 the previous UTC day's close is finalized, so the first slot publishes;
  a transient failure is caught up by a later slot the SAME day. Once the line is written, each later slot is a
  no-op "nothing due" — idempotent, proven offline by the L-4 replay. The service stays `Type=oneshot` (a clean
  journal); the retry lives in the timer, not in `Restart=`.

- **D3 — a keyed third operator, its URL out of the repo (L-3 / C-3 / C-4 / C-5).** When
  `CHAINSTACK_ETH_URL` is set, the pool gains it as a **ninth endpoint and a distinct operator** (`providerOf`
  → `chainstack.com`, not among the 8 free providers) in the round-robin rotation — no ordering privilege is
  claimed (`quorumTwo` rotates `rr`). `providerOf` is left **byte-identical** (imported under contract by Bell
  `operators.ts`/`quorum.ts` and `ukemi/rpc2.ts`); the sentinel holds only ONE Chainstack URL, so no p2pify
  merge is needed here. The URL is read ONLY in `main()` (via `poolEndpoints(env)`), never at module scope nor
  in `makeRpcPool` defaults, so the injected-`endpoints` test path never consults the env. The end JSON gains
  `chainstack: boolean` for visibility (a silently key-less run is diagnosable). The key lives in
  `EnvironmentFile=-/etc/monark/sentinel.env` (`root:sentinel 0640`, never committed); the leading `-` makes it
  optional — absent, the base 8-endpoint pool stays fail-closed and keeps publishing.

- **D4 — the endpoint URL is never printed (C-1, bloquant).** `run.ts:160` publishes `prov.endpoints` in every
  served line (`narabi-snapshot.ts`), so a raw Chainstack URL would put the key ON THE SITE. Fix: the 8 public
  URLs are published **verbatim** (`PUBLIC_ENDPOINTS` unchanged); the Chainstack endpoint is published
  **redacted to its origin** (`redactEndpoint` → scheme + host, never path/query — `publishedEndpoints`). Every
  error carrying a URL is reduced to `HTTP <status> <origin>` (`defaultCall`). `endpoints` is outside
  `hashedFields`, so redaction does not touch `line_hash`. `sentinel_never_prints_endpoint_url` asserts on the
  **error**, the **written line**, and **stdout**; the mutant "raw URL" reds each.

## Exit-code semantics (D1)

| `report.stopped` | meaning | `exit_code` | lines written |
|---|---|---|---|
| `null`, `due != []`, all processed | caught up | 0 | N >= 1 |
| `null`, `due == []` | up to date, or waiting for finality | 0 | 0 |
| `fetch_error:D:...` | RPC / quorum failure at day D | 1 | days before D (partial) |
| `quorum_disagreement:D` | two endpoints disagreed (fail-closed) | 1 | days before D |
| `unfinalized_to_block:D` | belt: `to_block > finalized` | 1 | days before D |
| `c1_fail:D` | C1 identity broke (fail-closed) | 1 | days before D |
| `catchup_budget` (sub-lot -1c, 2026-09-21) | the per-run TIME budget was exceeded BETWEEN two due days (the first due day is always attempted) | 1 | days processed before the stop (partial; the next slot resumes at prevDay+1) |
| `--dry-run` (any of the above) | inspect only — same stop/exit semantics, nothing written | 0 or 1 (mirrors the run) | 0 |

### Amendment 2026-09-21 (sub-lot NARABI-OPS-1b-ii-b — detection hardening; L-6b)

The DETECTION probe gains a second bounded GET of the served `/narabi/state.json` and cross-checks its `digest`
against the last timeline line's `digest_T` (the fact-5 invariant, measured VRAI on `NARABI_SNAPSHOT`), so a
PARTIAL publication (the window `run.ts:190`→`:191` where the public timeline is fresh but `public/state.json`
is still stale) is caught. Consequences:

- **`narabi.json` `reason` closed set gains `state_mismatch` and `state_unreachable`** (Q4): the state digest
  differs -> `state_mismatch`; the 2nd GET fails OR the body yields no comparable digest -> `state_unreachable`
  (a DISTINCT reason from a GET₁ `unreachable`). Precedence, FIXED: cannot-evaluate (`insecure_url`/`unreachable`/
  `too_large`/`probe_error`) > `chain_broken` > `state_unreachable` > `state_mismatch` > `lag`.
  *Amendment dated 2026-10-04 (orchestrator, lot PROBE-BADPORT-REASON-1, merge `728bd6b5`)*: the closed `reason` set gains `bad_port`,
  a cannot-evaluate reason ranked with `insecure_url`: a probe URL whose port is one the runtime's `fetch` refuses is refused before
  any call (list copied from node v24.15.0 with its provenance and pinned by a test against the embedded source; journal
  `docs/G1-lot-probe-badport.md`). A `PROBE_STATE_URL` on such a port stays `state_unreachable` (item PROBE-BADPORT-STATE-1).
- **`narabi.json` gains `state_checked: boolean`** (true iff the digest was compared). This joins the schema-2
  shape whose `schema` bump (with `alerted`/`alert_error`/`last_alert_day`) is added by sub-lot -1b-ii-a; this
  sub-lot did not touch the `SCHEMA` constant (kept as one edit at the -a/-b merge).
- **The state.json URL is DERIVED by basename replacement** from the timeline URL (env `PROBE_STATE_URL`
  overrides), so no extra config is needed (C-B-12). GET₂ is bounded on its own (`STATE_MAX_BYTES` 64 KiB,
  `STATE_TIMEOUT_MS` 5 s, `STATE_RETRIES` 1 fixed) — the GET₁+GET₂ capped worst case stays under
  `monark-probe.service TimeoutStartSec` without re-raising it.
- **Residual, declared (C-NB-4)**: a publication landing in the sub-second window between GET₁ (timeline) and
  GET₂ (state.json) can flag a transient `state_mismatch` that self-heals on the next shot; the flap is
  acceptable. A hardening option (re-read the timeline once before concluding) is a FORMED item, trigger = first
  observed false `state_mismatch` at deploy, owner orchestrator.
- **`monark-sentinel.service` gains `TimeoutStartSec = max(300, ceil(3*D/60)*60) = 300 s`** (D = 25.481 s, the
  measured publishing run; `RUN_DURATION_D_SEC=26`). It lives on the **VPS SITE** (not Bell), so its redeploy is
  **E-5 (investor decision 92)**, per RUNBOOK §6.

The `probe → alerte` mail channel and the schema-2 state machine are sub-lot **-1b-ii-a**.

### Amendment dated 2026-09-21 (sub-lot NARABI-OPS-1c, checkpoint-1 C8 - its own G0/ADR per investor decision 109) - bounded catch-up per run
- **Context (measured, PLI -1b-ii-b section 10.2).** `runDue` accumulates every due day in memory and `main` writes only after it returns, so a `TimeoutStartSec=300` kill during a multi-day backlog writes nothing and the next slot recomputes the same due list (catch-up livelock, RUNBOOK section 6 Mode A). `D = 25.481 s` for one due day (ONE point, healthy pool) gives a threshold of about 12 backlog days.
- **Decision.** A per-run TIME budget checked BETWEEN due days, with an injected clock: default 180 s, `MONARK_SENTINEL_BUDGET_S` integer 30..180 (else throw), first due day always attempted, stop = `stopped:"catchup_budget"` so the L-1 contract (`stopped != null <=> lag >= 1 <=> exit 1`) is unchanged; lines already produced are written by the existing single append block; the next timer slot resumes at prevDay+1. Inter-file invariant pinned by a test: `BUDGET_MAX_S (180) + MARGIN_MIN_S (120) <= TimeoutStartSec` read from `deploy/monark-sentinel.service`. The end JSON gains `elapsed_ms` and `max_day_ms`; the published LINE and its hash are unchanged.
- **Rejected.** Per-day checkpoint writes inside `runDue` (changes the write/exit order and the torn-line window, Mode B); a fixed `--max-days` (does not protect against one slow day); `TimeoutStartSec=infinity` (loses the safety backstop); systemd `Restart=` (excluded by L-1).
- **Pre-registered criterion of NO.** A production run showing `max_day_ms > 60 000` (half the margin) triggers a dated amendment re-deriving the default budget; margin = `max(120, ceil(k * D_max))`, `k = 4`, fixed before the code.
- **Residual modes, DECLARED (decision 109 is REDUCED, not lifted).** (i) A-prime: a SINGLE day exceeding 300 s (slow pool without a fault, or a late `fetch_error`: `one()` may rotate 9 endpoints x 20 s = 180 s per call); (ii) a slow day exceeding the margin AFTER the budget stop loses the lines of that run. Both stay DETECTED (external probe: `lag`, mail, one reminder per UTC day) and are repaired by RUNBOOK section 6 A.1, which is KEPT. Closing (ii) (a hard intra-run deadline through `rpc.ts`) is a scope change: separate lot, trigger = first production `max_day_ms > 60 000`, owner orchestrator.
- **Residual (iii), declared at checkpoint-2 (C2, 2026-09-21; error_origin validator + orchestrator: not seen at checkpoint-1).** The budget clock `t0` is taken INSIDE `runDue`; the preamble (`loadState`, then the sequential `finalized()` quorum, up to 20 s per hanging endpoint) is counted neither in the budget nor in `elapsed_ms`, and `BUDGET_MAX_S (180) + MARGIN_MIN_S (120) = 300 = TimeoutStartSec` leaves it no slack. It is part of residual (ii). The pre-registered criterion of NO gains a second condition: **systemd wall-clock duration minus `elapsed_ms` > 30 000 ms** on a production run triggers the same dated amendment. Counting the budget from the start of `main` is a code change to a SEPARATE lot (it would change the deployed `run.ts` sha); not required here.
- **Pipes.** Unchanged: `timeline.jsonl` / `state.json` -> `/narabi/` (site) and the Bell probe (`built`); no served consumer parses `stopped` values.

## Risks (MAST)

  origin; `sentinel_never_prints_endpoint_url` asserts error + line + stdout; `no_secret_in_repo` scans the

  write-skip reds).
- **A key in a log** — counter: `defaultCall` error carries the origin only.
- **Silent key-less degradation** (EnvironmentFile absent ⇒ back to the free pool that caused the incident) —
  accepted over "refuse to start" (a unit that will not start publishes nothing, with no alert channel yet, a

- **Duplicated hash-order drift in the probe** — deferred with the probe (pli 1b); countered there by

- **Four RPC reads/day** — cost: three no-op runs = two `finalized` reads each, negligible.
