## 2. Construction

### 2.1 La forme, et l'ordre des contrôles d'`io_guard`

- `FORM = ("-E", "-S", "-s", "-B", "-P")` (`io_guard.py` l.48) ; le poids de `safe_path`, dernier des 17 de l.49, passe de 0 à 1.
  `run_tool` (l.429-433) lance ses enfants sous `FORM` : ils prennent `-P` sans autre ligne.
- **Les contrôles passent avant tout autre import.** Les l.37-42 deviennent `import os` et `import sys` (gelé, intégré : rien
  n'est cherché par son nom) ; suivent le contrôle de la forme (l.44-57, commentaire inchangé), le refus d'un `io_guard.py` qui est un
  lien et le contrôle de la liste (§2.3), celui de la liste du second arbre quand il existe (§2.6), celui de la route 3a (§2.5), puis
  `import hashlib`, `subprocess`, `sysconfig` et `threading`. Ordre : la forme d'abord (un lancement dévié sort en 2, ses champs
  nommés, comme aujourd'hui, et les cas `launch` de `guard_check.py` gardent leur texte), les listes ensuite (sortie 4).
- Raison de l'ordre : sous l'ancienne forme, le dossier du script est `sys.path[0]`, et les imports d'`io_guard` y cherchaient d'abord
  (la route des homonymes). Contrôles en tête, un lancement sous l'ancienne forme s'arrête en 2 avant toute recherche : mesuré, un
  `threading.py` posé et `python -E -S -s -B` sur `candA` sortent en 2 (« safe_path False »), le témoin ne tourne pas.
- Effet de bord mesuré (`probe_install.py`, copie de l'interpréteur dont les caches ont été retirés) : un lancement sans `-B` qui
  importe `io_guard` (le dernier cas `launch` de `guard_check.py`) écrit aujourd'hui 22 fichiers de cache dans une installation
  inscriptible, ceux des imports d'`io_guard` ; sous `candA`, 4, ceux du démarrage de l'interpréteur (`linecache`, `encodings` ×3).

### 2.2 Le prologue des huit scripts d'entrée : `io_guard.py` lancé par son chemin

Cinq lignes, identiques dans les huit scripts (`binom_check.py`, `compare_check.py`, `compare_p2.py`, `guard_check.py`, `recalc_p2.py`,
`report.py`, `report_check.py`, `vectors_check.py`), juste avant leur ligne `import io_guard`, qui reste (texte de la sonde, largeurs
135, 130, 124, 103, 80) :

```python
import os, sys  # sys built in, os frozen: no file is looked up by name before io_guard has checked its folder (IO-GUARD-POSED-FILES-1)
if "io_guard" not in sys.modules:  # io_guard.py run by its path, never found by name: nothing posed or installed stands in for it
    sys.path.append(_d := os.path.dirname(os.path.realpath(__file__)))  # the tool's folder, last in sys.path: -P is in FORM
    _g = sys.modules["io_guard"] = type(sys)("io_guard"); _g.__file__ = os.path.join(_d, "io_guard.py")
    exec(compile(open(_g.__file__, "rb").read(), _g.__file__, "exec"), vars(_g))
```

- **Ce qu'il fait.** Sous la forme, avant `io_guard`, le prologue ne lit qu'un fichier, `io_guard.py`, par son chemin ; `os` est gelé,
  `sys` intégré, et `type(sys)` donne le type module sans `import types`, qui serait une recherche par nom. `io_guard.py` n'est
  jamais cherché : ni un paquet `io_guard/`, ni un cache, ni un module d'extension `io_guard.<suffixe>` (qui passerait aussi avant la
  source), ni un `io_guard.py` posé dans l'installation ou dans un `python314.zip` ne peut le remplacer (mesuré pour le paquet, le
  cache et l'installation, §1). Le dossier va en fin de `sys.path` (la ligne mesurée à `24f50372`), pour les onze autres modules, importés
  ensuite par leur nom.
- **Une fois par processus.** Un script d'entrée importé par un autre (`report` par `report_check` ; `recalc_p2` par `vectors_check`,
  par `report` et par `report_check`, l.26 ; `compare_p2` par `report`) trouve `io_guard` dans `sys.modules` : le garde ne tourne
  qu'une fois, le dossier n'est ajouté qu'une fois (l'idempotence que la note de `24f50372`, l.2161-2163, demandait).
- **Ce qui change pour le module** : `io_guard.__spec__` et `__loader__` valent `None`. Aucun fichier de l'outil ne les lit (lu) ; tout
  `import io_guard` ensuite rend le module de `sys.modules`. Les lancements `-c` de `_launch` (`guard_check.py` l.152-160), qui testent
  les autres formes, importent toujours `io_guard` par son nom depuis la copie posée en tête : ils ne passent pas par le prologue.
- **Sortie** : `io_guard.py` absent ou illisible, l'`open` du prologue lève, la course sort en 1, comme Python le fait de toute
  exception non rattrapée ; aucun rapport (mesuré : `FileNotFoundError`, sortie 1). La table des sorties le dit (§3).
- **Voie écartée (Q-1 : oui au prologue, MONARK `296ca05`)** : garder `import io_guard` par son nom et vérifier dans le prologue
  qu'aucun nom du dossier ne peut le masquer (`io_guard*` autre qu'`io_guard.py`, `__pycache__` en toute casse). Un prix voisin (4
  lignes au lieu de 5), mais elle ne ferme pas l'installation, et elle repose sur une liste de motifs (les suffixes des chargeurs) qui
  suit les versions de Python.

### 2.3 La liste close `FILES`

- **Où elle vit** : dans `io_guard.py`, un tuple des douze noms du dossier, triés : `FILES = ("binom_check.py", "binom_exact.py",
  "compare_check.py", "compare_p2.py", "fdlibm_log.py", "guard_check.py", "io_guard.py", "kata_lib.py", "recalc_p2.py", "report.py",
  "report_check.py", "vectors_check.py")`, juste après le contrôle de la forme. Pas de fichier de liste à part : il serait un nom de
  plus à lister, et lu avant tout import.
- **Comment elle est épinglée** : `io_guard.py` est l'un des douze blobs de l'arbre ; la liste bouge donc avec l'empreinte de l'arbre,
  que la liste des vérificateurs de 1f épingle (§4). Un test Node neuf tient `FILES` égal aux noms des entrées de l'index sous
  `tools/kata-recalc/` et à ceux du dossier de travail (§5.2) : un fichier ajouté à l'arbre sans `FILES`, ou un nom de `FILES` sans son
  fichier, rougit. Tout lot qui ajoute un fichier à l'outil écrit donc `FILES` dans le même commit.
- **Le dossier, un seul** (pli m-4) : celui que le prologue ajoute à `sys.path`, pris dans le `__file__` d'`io_guard`, dossier résolu,
  nom non résolu (la règle d'`_entry`, l.163-166 : `realpath` du dossier, puis le nom tel quel). La liste, la route 3a (§2.5) et le
  reste du garde (`_TOOL_DIR`, l.173) jugent ce même dossier. Avant toute liste, un `io_guard.py` qui est un lien est refusé, sortie 4,
  par son propre texte (« a link ») : son `realpath` mènerait hors du dossier qui sert les onze autres modules. v1 (la sonde,
  `mkcand.py` l.42) prenait le dossier après résolution du nom : un `io_guard.py` lien faisait juger un autre dossier que celui du
  chemin d'import, et seule la route 3a, par effet de bord et sous le texte d'une autre cause, refusait ce cas. Raisonné sur le code
  de la sonde et du tronc, non mesuré (v2 n'ajoute aucune sonde) ; prix : 2 à 3 lignes d'`io_guard`, un cas (§5.1).
- **Le contrôle** : `os.listdir` de ce dossier, comparé à `FILES` par chaînes exactes, casse comprise. Refusés : tout nom en trop
  (fichier, dossier, lien, `__pycache__`), et tout nom de `FILES` qui n'est pas un fichier ordinaire (`os.path.islink` ou non
  `os.path.isfile` : un nom manquant, un dossier, un lien ; `os.path` est gelé). Le refus : une ligne sur stderr qui nomme les noms,
  puis `os._exit(4)` (`REFUSED_EXIT`, la classe du refus du cache, l.454-455 ; Q-8 : 4), avant tout autre import.
  Texte de la sonde : `io_guard: refused import ['msvcrt.py']: a name of the tool's folder outside its closed list FILES, or not a file`.
- **La casse.** Sous NTFS, `__PYCACHE__` est le dossier de cache pour le système (l'import ouvre `__pycache__\…` sans tenir compte de la
  casse) ; la comparaison exacte le refuse comme un nom en trop. Un nom de `FILES` écrit dans une autre casse est refusé comme nom en
  trop (sous POSIX, aussi comme manquant ; sous NTFS, `isfile` le trouve). Rien ne dépend de `PYTHONCASEOK` : `-E` le fait ignorer.
- **Ce qu'elle ferme** (§1) : homonymes, `msvcrt`, `_wmi`, fichier et dossier en trop, cache dans toute casse, sous toute forme ; avec le
  prologue, le paquet et le cache d'`io_guard`. Sous Windows, `msvcrt` est intégré et `_wmi` un module de `DLLs` : un leurre sous ces noms
  n'y est jamais atteint (prédit, rejoué par MONARK), et la liste le refuse quand même. Les noms qu'une installation Windows cherche
  sans les trouver (les imports facultatifs de POSIX) sont refusés de même, quel que soit leur inventaire : le point 4 de la mesure
  devient une information, plus une condition.
- **Ce qu'elle ne ferme pas** : un nom posé après le contrôle, pendant la course (§2.4) ; l'installation (§2.5, §11) ; un fichier listé
  dont les octets changent (l'épingle : `tool_identity` de `report.py` l.154-170 en course, et le test d'arbre ; hors de ce lot).
- **Refus à tort** : une copie d'éditeur (`report.py~`, `.report.py.swp`), un `desktop.ini`, un `__pycache__` laissé par un lancement
  sans `-B` : refusés, nommés ; l'opérateur les retire. Le refus est fermé.
