## Faits mesurés (relecture first-hand du code + ADR + décisions, 2026-09-20)
1. **[lu, code]** La surface publiée par le sentinel est **exactement deux fichiers** : `run.ts:186-191` écrit `timeline.jsonl` (append) et `state.json`, puis les **copie** dans `public/` (servi par Caddy `handle_path /narabi/*`, `deploy/Caddyfile.monark-narabi.snippet`, confirmé `test/narabi-live.test.ts:164-189`) — URL `https://monarkgate.tech/narabi/{timeline.jsonl,state.json}` (`RUNBOOK-sentinel.md:118`). **Ni `chainstack` ni `exit_code` ne figurent dans ces fichiers** : ils ne vivent que dans le JSON de fin sur **stdout / journalctl** (`run.ts:180`), invisible de l'extérieur. Conséquence directe : la sonde externe **ne peut lire ces deux champs tels quels** ; elle doit les inférer de la surface servie (voir faits 2-3) ou exiger un fichier de santé publié (Q1, hors L-n par défaut).
2. **[lu, code] `exit_code` du run PUBLIANT a un proxy externe exact.** `run.ts:175` : `exitCode = report.stopped !== null ? 1 : 0` ; table `ADR-NARABI-OPS-1.md:63-73` : `exit_code = 1` **⟺** `stopped != null` **⟺** un jour dû non rattrapé. Donc **une ligne J−1 fraîche et chaînée implique que le run qui l'a ÉCRITE a fini `exit_code = 0`** (un `stopped != null` n'écrit jamais la ligne du jour fautif — `run.ts:182` n'écrit que si `report.lines.length > 0`). **Portée exacte** : la fraîcheur J−1 prouve le code du **run publiant**, pas de chaque créneau. Un créneau de retry peut `FATAL` **avant** le JSON de fin (`run.ts:201` : `finalized()` sans quorum lève, `process.exitCode = 1`, **rien d'écrit, aucune trace externe**) ; c'est **bénin** quand J−1 est déjà publié (retries no-op) et **capté** par la fraîcheur quand J−1 manque encore. Le seul cas invisible sans `health.json` = un créneau qui FATAL alors que le jour est déjà sain (non-incident) ⇒ renforce le report de `health.json` (Q1 : indicateur avancé, non bloquant).
3. **[lu, code] `chainstack: true` a un proxy externe.** `rpc.ts:68-71` `publishedEndpoints` publie les **8** URLs publiques verbatim **+** l'endpoint Chainstack **expurgé à son origine** (hôte seul, `redactEndpoint` `rpc.ts:41-47`) quand la clé est présente ; ce tableau `endpoints` est porté par **chaque ligne** de `timeline.jsonl` (`timeline.ts:64-65`, hors champs hachés — `hashedFields` `timeline.ts:94-101` s'arrête à `prev_line_hash`). Donc `chainstack_present = endpoints.some(e => providerOf(e) ∈ {chainstack.com, p2pify.com})` — **jamais** un index positionnel `endpoints[8]` ni `length === 9` (fragile : `PUBLIC_ENDPOINTS` `rpc.ts:19-23` peut gagner/perdre un hôte gratuit). La sonde lit ce proxy sur la dernière ligne ; l'absence est un **fait enregistré** (dégradation silencieuse vers le pool gratuit — cause de l'incident, `ADR-NARABI-OPS-1.md:114-116`), inclus au corps d'alerte, jamais un mail dédié par défaut (Q2).
4. **[lu, ADR] Spécification de reprise de la sonde (L-5 différé).** `ADR-NARABI-OPS-1.md:84-104` : `scripts/probe-narabi.mjs` en **built-ins Node seuls** (`@monark/*` non importable sur Bell : `timeline.ts` importe hikae/harness, C-8), **duplique l'ordre des 31 champs `hashedFields`** et recompute `line_hash = sha256(JSON.stringify(les 31 champs))` ; GET `/narabi/timeline.jsonl`, vérifie dernière `day == J−1` (après 10:00 UTC), continuité `prev_line_hash`, `line_hash` recomputé ; écrit `{ok,last_day,lag_days,checked_at}` dans `/var/lib/monark-probe/narabi.json` ; **exit 1 si `lag_days > 0`** ; injecte `--file`/`--now` (ou env) pour les tests hors ligne. ## Risques (MAST)
- **Faux négatif de fraîcheur** (la sonde manque un lag) ⇒ échéance ≥ 10:30 UTC ancrée sur le dernier créneau + jitter (fait 5) ; `probe_narabi_detects_lag` J−2 ⇒ exit 1.
- **Faux POSITIF au reboot / `systemctl start`** (`Persistent=true` ⇒ run avant le créneau 00:30 ⇒ J−1 légitimement absent ⇒ mail à tort) ⇒ **gril d'échéance dans la LOGIQUE** (`expected_last_day`, L-1 b), pas seulement dans le timer ; test `--now …T00:15Z` ⇒ healthy ; mutant gril retiré ⇒ rouge.
- **Créneau qui `FATAL` sans trace externe** (`run.ts:201`, `finalized()` sans quorum) ⇒ invisible de l'extérieur mais **bénin** si J−1 déjà publié ; capté par la fraîcheur si J−1 manque ; visibilité par créneau = `health.json` (Q1, non bloquant).
- **Chaîne rompue non détectée** (recompute sauté) ⇒ duplication fidèle des 31 champs + `probe_line_hash_equals_sentinel_lineHashOf` + mutant recompute-sauté.
- **Dérive de l'ordre de hash dupliqué** (Bell ne peut importer `timeline.ts`) ⇒ oracle d'égalité sur les lignes committées ; tout changement des champs hachés côté sentinel casse ce test au prochain rejeu (dette de couplage **déclarée**, item : re-vérifier à chaque évolution de `hashedFields`).
- **Tempête d'alertes** (un mail par run) ⇒ machine à états à un bit, `alerted` persistant, un mail par transition ; mutant ré-alerte ⇒ rouge.
- **Secret dans un log / le dépôt** ⇒ `SMTP_PASS`/`ALERT_TO` hors dépôt (env `0640`), jamais imprimés ; `no_secret_in_repo` ; **aucun certificat TLS committé** (fait 8).
- **Plaintext SMTP hors loopback** (fuite d'identifiants) ⇒ garde loopback + `probe_smtp_refuses_plaintext_off_loopback`.
- **Handshake SMTP incorrect** (465 vs 587, AUTH) ⇒ 465 TLS implicite par défaut (moins d'états) ; 587 STARTTLS en repli ; **conversation exercée par le factice loopback**, TLS réel exercé au déploiement (mail de test, go).
- **Sonde muette elle-même** (Bell/probe mort ⇒ aucune alerte) ⇒ **dead-man switch = Q4/item formé** (jamais un dû nu).
- **Dégradation chainstack silencieuse** (pool gratuit, cause de l'incident) ⇒ proxy `chainstack_present` enregistré + inclus au corps d'alerte ; mail dédié = Q2.
- **`p2pify.com` au lieu de `chainstack.com`** (item i) ⇒ `providerOf ∈ {chainstack.com, p2pify.com}` accepté, confirmé au déploiement sans imprimer la variable (lecture de l'origine expurgée publiée).

## Hypothèses testables
1. **Une ligne J−1 fraîche + chaînée ⟹ le run PUBLIANT a fini `exit_code 0`** (fait 2 ; portée = le run publiant, pas chaque créneau — un FATAL de retry `run.ts:201` reste invisible mais bénin) — falsifiable : un `stopped != null` n'écrit jamais la ligne du jour fautif (`run.ts:182`).

4. **465 TLS implicite est accepté par `smtp.hostinger.com`** (fait 10) — falsifiable au déploiement (mail de test) ; 587 STARTTLS en repli si non.
5. **`expected_last_day` ne bascule à J−1 qu'après l'échéance ≥ 10:30 UTC (= dernier créneau + jitter + durée du run + latence)** — falsifiable : avant l'échéance, `expected = today−2` (pas de fausse alerte au reboot) ; la durée du run est **non mesurée** (item) ; `publish_latency` enregistré pour calibrer, marge élargie si un faux positif apparaît.
